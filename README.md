# gdebenz_server

Потенциально совместимый авторитетный WebSocket-сервер для игры
[`citi_ads`](https://github.com/Evsikoff/citi_ads). Исходники клиента не изменяются.

Сервер:

- принимает имя, управление или координаты игрока и взаимодействия с объектами;
- генерирует детерминированную карту в формате клиентского `City`;
- симулирует физику игроков, расход топлива и движение ботов;
- передаёт позиции игроков и ботов всем клиентам;
- управляет АЗС, рекламными щитами, канистрами и единственной базой;
- ведёт общую турнирную таблицу игроков и ботов по залитым за заезд литрам;
- убирает проигравших игроков с карты и респаунит игроков и ботов в случайных местах на дорогах;
- уменьшает число ботов на одного при каждом подключении игрока;
- перестраивает карту при росте или уменьшении числа игроков и добавляет ранее подключённым игрокам до 10 л топлива.

## Запуск

Нужен Node.js 22 или новее.

```bash
npm install
npm run dev
```

По умолчанию:

- WebSocket: `ws://localhost:8080/ws`
- проверка состояния: `http://localhost:8080/health`
- краткая информация о протоколе: `http://localhost:8080/protocol`

Для production:

```bash
npm run build
npm start
```

Переменные окружения перечислены в `.env.example`: `HOST`, `PORT` и список
разрешённых origin через запятую в `ALLOWED_ORIGINS`. Значение `*` разрешает
подключение с любого origin.

Docker:

```bash
docker build -t gdebenz-server .
docker run --rm -p 8080:8080 gdebenz-server
```

## Игровые настройки

Все числа находятся в [`src/config.ts`](src/config.ts). Файл повторяет настройки
клиента (`botCount`, расход топлива, таймауты, стартовые ресурсы, цены и лимиты
АЗС) и добавляет серверные частоты, параметры карты и ограничения протокола.

Правило количества ботов:

```text
bots = max(0, CONFIG.botCount - connectedPlayers)
```

Правило масштаба карты реализовано буквально по требованиям:

```text
ratio = connectedPlayers / CONFIG.botCount
scale = ratio > 2 ? floor(ratio) : 1
```

`scale` увеличивает обе стороны карты. Поэтому площадь, число АЗС, канистр и
рекламных щитов растут в `scale²` раз и объекты равномерно распределяются по
новой площади. База во всех случаях одна.

При любом изменении `scale` сервер:

1. увеличивает `worldRevision` и генерирует новую карту;
2. рассылает `world:map-update` уже подключённым игрокам;
3. добавляет каждому из них `min(10, tankVolume - fuel)` литров;
4. ограничивает координаты новыми границами и пересоздаёт нужное число ботов.

Новый игрок, вызвавший изменение размера, бонус не получает: он сразу начинает
со стартовым баком из конфигурации.

## WebSocket-протокол v1

Каждое сообщение — JSON-объект:

```json
{
  "type": "player:join",
  "payload": { "name": "Ева" }
}
```

Сразу после соединения сервер отправляет `server:hello`. До присоединения клиент
может отправлять только `player:join` и `ping`.

### Сообщения клиента

#### `player:join`

```json
{ "type": "player:join", "payload": { "name": "Ева" } }
```

В ответ приходят `player:welcome` и полный `world:snapshot`.

#### `player:input` — рекомендуемый авторитетный режим

```json
{
  "type": "player:input",
  "payload": {
    "seq": 14,
    "worldRevision": 1,
    "up": true,
    "down": false,
    "left": false,
    "right": true,
    "handbrake": false
  }
}
```

`seq` должен монотонно увеличиваться. Сервер применяет те же базовые значения
разгона, торможения, максимальной скорости и поворотливости, что и клиент.

#### `player:booster`

```json
{
  "type": "player:booster",
  "payload": { "requestId": "boost-1", "systemName": "speed25", "cost": 1250 }
}
```

Эффект бустера применяет сервер: скорость, расход, топливо и деньги — его
состояние, и начисленное клиентом самому себе всё равно затёрлось бы ближайшим
снимком. Понимаются `speedN`, `consumptionN`, `fuelNl` и `moneyN`; `cost` —
сколько списать игровой валютой (0 или отсутствует для покупок за деньги и
рекламу). Ответ приходит в `game:event-result` с событием `booster-applied` и
полями `revived`, `spent`, `speedMultiplier`, `fuelConsumptionMultiplier`.
Заглохшему игроку разрешён только топливный бустер: он поднимает машину и
сопровождается `player:respawned`.

#### `player:move` — режим совместимости с текущей локальной физикой

```json
{
  "type": "player:move",
  "payload": {
    "seq": 15,
    "worldRevision": 1,
    "x": 5235,
    "y": 6400,
    "angle": -1.57,
    "speed": 310
  }
}
```

Сервер проверяет последовательность, ревизию мира, границы и физически возможное
расстояние между обновлениями. Этот режим позволяет сначала подключить текущий
`CityRideGame`, а позже перенести физику целиком на сервер без смены остальных
сообщений.

#### `world:interact`

```json
{
  "type": "world:interact",
  "payload": {
    "requestId": "action-42",
    "objectType": "station",
    "objectId": "station:4:7",
    "amount": 12.5
  }
}
```

Поддерживаемые объекты:

| `objectType` | Действие | `amount` |
| --- | --- | --- |
| `canister` | подобрать канистру, увеличить бак на 10 л | не нужен |
| `billboard` | включить cooldown и открыть случайную АЗС | не нужен |
| `station` | купить бензин, заблокировать АЗС и запустить таймер | желаемые литры, необязательно |
| `base` | продать не более половины текущего топлива | литры, необязательно |

Перед действием сервер проверяет расстояние игрока до объекта и актуальное
состояние объекта. Ответ — `interaction:result` с тем же `requestId`.

#### События совместимости с локальной игровой механикой

Если клиент продолжает сам покадрово рассчитывать заправку, он передаёт факты
отдельными сообщениями. При первом фактическом начале заправки:

```json
{
  "type": "station:blocked",
  "payload": { "requestId": "lock-42", "stationId": "station:4:7" }
}
```

Сервер сразу блокирует АЗС и рассчитывает время до открытия другой случайной:

```text
unlockIn = CONFIG.stationTimeoutBase
         + CONFIG.stationTimeoutPerCanister * player.canisters
```

АЗС, активированная рекламным щитом (`origin: "ad"`), после использования не
создаёт следующую цепочку таймера — это повторяет офлайн-логику игры.

Каждый фактически залитый объём передаётся как положительная дельта в литрах:

```json
{
  "type": "player:fuel-filled",
  "payload": {
    "requestId": "fuel-42-1",
    "stationId": "station:4:7",
    "liters": 0.16
  }
}
```

Сервер проверяет близость к АЗС, свободный объём бака, деньги и накопленный лимит
колонки, обновляет ресурсы игрока и его результат в таблице. Для одной сессии
следует сначала отправить `station:blocked`, затем одну или несколько дельт
`player:fuel-filled`.

Взаимодействие с рекламным щитом передаётся отдельно:

```json
{
  "type": "billboard:interacted",
  "payload": { "requestId": "ad-42", "billboardId": "billboard:12" }
}
```

Сервер переводит щит в cooldown и активирует случайную заблокированную АЗС.

Для одной заправки клиент выбирает один режим: либо единый серверный
`world:interact` со станцией, либо пару `station:blocked` и
`player:fuel-filled`. Одновременная отправка обоих вариантов означала бы два
разных игровых действия.

Все пять сообщений ниже идемпотентны по `requestId`: повтор пакета возвращает
тот же `game:event-result`, но повторно не меняет мир. `requestId` должен быть
уникальным для каждого нового игрового события.

#### Проигрыш и респаун

```json
{
  "type": "player:lost",
  "payload": { "requestId": "lost-42", "reason": "out-of-fuel" }
}
```

Сервер останавливает игрока, убирает его из `world:entities` и рассылает
`player:despawned`. Строка игрока остаётся в `leaderboard:update` с
`active: false`, поэтому финальный результат заезда виден остальным.

```json
{
  "type": "player:respawn",
  "payload": { "requestId": "respawn-42" }
}
```

Респаун возвращает ту же сетевую сущность в случайное свободное место на дороге текущей карты, сбрасывает бак,
топливо, деньги, канистры и литры заезда до стартовых значений и рассылает
`player:respawned`. Игрок не переподключается, поэтому число ботов и масштаб
карты от проигрыша или респауна не меняются.

#### `ping`

```json
{ "type": "ping", "payload": { "clientTime": 1756300000000 } }
```

Ответ: `pong` с `serverTime`.

### Сообщения сервера

- `server:hello` — версия протокола и частоты симуляции/снимков;
- `player:welcome` — id и начальное состояние своего игрока;
- `world:snapshot` — полная карта, игровые сущности и текущая таблица после входа;
- `world:entities` — частые позиции и ресурсы игроков, состояния ботов;
- `world:collisions` — столкновения машин за тик: точка удара, сила, кто кого
  протаранил и сколько канистр выбило;
- `player:refuel` — заправка началась или закончилась, с причиной остановки;
- `world:objects` — изменившиеся состояния АЗС, щитов и канистр;
- `world:map-update` — полная новая карта после изменения масштаба;
- `player:joined`, `player:left` — изменение состава комнаты;
- `player:despawned`, `player:respawned` — проигрыш и возвращение игрока;
- `leaderboard:update` — отсортированный рейтинг всех игроков и ботов;
- `interaction:result` — результат действия с объектом;
- `game:event-result` — идемпотентный ответ на совместимые игровые события;
- `server:error` — отклонённое или неверное сообщение;
- `pong` — ответ на `ping`.

Координаты всех игроков и ботов в `world:entities` относятся к указанному там
`worldRevision`. Клиент не должен применять пакет от старой ревизии после
`world:map-update`.

### Заправка

Заправку ведёт сервер, а не одно мгновенное действие клиента: пока машина
стоит на площадке работающей АЗС, топливо льётся по `refuelRate` литров в
секунду, деньги списываются пропорционально цене колонки. Колонка блокируется
сразу, как только к ней встали, и тогда же в очередь становится открытие
другой случайной АЗС. Останавливают заправку полный бак, лимит колонки или
деньги в кармане — что первым закончится; начатую сессию сервер доводит до
конца, даже если по дороге лимит уже выбран. Под колонкой машина стоит с
заглушённым мотором: скорость обнуляется и топливо не расходуется. Повторно
встать под ту же колонку, не съехав с площадки, нельзя — иначе долитый бак
тратил бы пару капель и заправка начиналась бы заново.

Ход сессии виден в снимке игрока (`refueling`, `refuelStationId`,
`refuelLiters`, `refuelSpent`), а начало и конец приходят событием:

```json
{
  "type": "player:refuel",
  "payload": {
    "playerId": "d1f0…",
    "stationId": "station:7",
    "state": "stopped",
    "reason": "limit",
    "liters": 20,
    "spent": 1840
  }
}
```

`reason` — `full`, `limit`, `money` или `left` (съехали с площадки).

### Активация конкретной АЗС

`world:interact` с `objectType: "station"` по **закрытой** станции открывает
именно её с `origin: "ad"` — это бустер «Активировать эту АЗС». Ответ содержит
`details.activated`, цену, лимит и число активных станций. Тот же запрос по
работающей станции остаётся режимом совместимости со старыми клиентами и
заправляет бак разом; актуальный клиент его не шлёт.

### Столкновения машин

Столкновения игроков и ботов между собой считает сервер — теми же правилами,
что и офлайн-режим клиента. Каждый тик пары кузовов сначала расталкиваются,
затем по скорости сближения вдоль оси удара определяется, кто кого протаранил:
таранивший получает отдачу, протаранённый — отлёт (`kx`/`ky` в снимке), бот
дополнительно оглушается на полсекунды, а его канистры разлетаются вокруг
места удара и полторы секунды недоступны для подбора. Машина, стоящая под
работающей колонкой, считается стенкой: её не отбросить и канистры из неё не
выбить. Лёгкое касание бортами (сближение медленнее 70 пикс/с) тараном не
считается — иначе машины в потоке бесконечно пинали бы друг друга.

Пакет уходит тем же тиком, что и удар, а сразу за ним принудительно
отправляется `world:entities` — иначе отскок доехал бы до клиента с задержкой
до следующего снимка:

```json
{
  "type": "world:collisions",
  "payload": {
    "tick": 1420,
    "collisions": [
      {
        "x": 3120.5,
        "y": 1874.2,
        "force": 480.3,
        "rammerId": "d1f0…",
        "victimId": "bot:3",
        "rammerIsPlayer": true,
        "victimIsPlayer": false,
        "spilled": 2
      }
    ]
  }
}
```

Строка таблицы имеет вид:

```json
{
  "entityId": "player-or-bot-id",
  "name": "Ева",
  "liters": 24.5,
  "isPlayer": true,
  "color": "#e5472f",
  "position": 1,
  "active": true
}
```

Сортировка совпадает с офлайн-игрой: сначала больше залитых литров, при равенстве
сохраняется исходный порядок участников.

## Формат карты

`world:snapshot.payload.map` и `world:map-update.payload.map` содержат структуру,
аналогичную `City` из клиента:

```text
blocks, parks, buildings, billboards, trees, lamps,
stations, base, canisters, roadCenters
```

Сервер добавляет каждому интерактивному или декоративному объекту стабильный
`id`, а также `meta`:

```json
{
  "revision": 1,
  "seed": 20260214,
  "scale": 1,
  "grid": 10,
  "worldSize": 10470,
  "blockSize": 860,
  "roadWidth": 170
}
```

Число `10470` следует непосредственно из формулы клиента:
`grid * blockSize + (grid + 1) * roadWidth`.

## Как подключить существующую игру позже

Текущая версия `citi_ads` полностью локальная и WebSocket пока не использует.
Минимальная будущая интеграция состоит из четырёх точек:

1. после меню открыть `/ws`, отправить `player:join` и заменить результат
   `buildCity(...)` картой из `world:snapshot`;
2. отправлять либо клавиши как `player:input`, либо состояние локальной машины
   как `player:move`;
3. вместо локального `createBots/stepBot` рисовать ботов и других игроков из
   `world:entities`;
4. направить подборы/заправку/щит/базу через `world:interact` и при
   `world:map-update` атомарно заменить `city`, фон мини-карты и `WORLD`.

Так сервер уже готов к совместной игре, но клиентский репозиторий остаётся без
изменений, как и требовалось.

## Проверки

```bash
npm run typecheck
npm test
npm run build
```

Тесты покрывают граничные значения формулы масштаба, пропорции карты,
детерминированную генерацию, уменьшение/восстановление числа ботов, топливный
бонус, игровые взаимодействия, таймер и случайную активацию АЗС, рейтинг,
идемпотентность, проигрыш/респаун, проверку сообщений и настоящий
WebSocket-handshake.
